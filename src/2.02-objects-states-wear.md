## In plain words

Every object in a lot, from a toilet to a lamp, is the same kind of thing underneath: a catalog entry that points at one tuning record, plus a bag of optional parts called components. A part gives the object one ability: holding states, burning, lighting up, sitting in an inventory, being carried, making puddles. Almost every object has the state part, and most of what you see an object "be" (dirty, broken, burnt, switched on, full of water) is a state.

States come in two kinds. Some are plain switches set by an action. Others follow a hidden number on the object: brokenness from 0 to 100, dirtiness from -100 to 100, a fire counter, a light level. The number moves, and when it crosses a band edge the state changes, which then swaps the material, plays effects, adds a puddle maker or cuts the object's value. Dirtiness bands overlap on purpose, so an object that has just turned dirty stays dirty until it is cleaned well past the line.

Things that would surprise a player: wear only happens through use. A toilet loses about 6.4 points of its 100 on two thirds of uses and breaks below 30, about 16 uses from new; an object never wears out by sitting still. A broken object is worth half its value and a burnt one nothing. Objects never lose value with age: apart from state changes, the only automatic cut is a single 20 percent when you buy something. Fire is a commodity countdown: one flame burns a normal object out in about 11 Sim minutes, a fire object burns itself out after about 90, and fire insurance pays half of what burned only while you own the lot and only when the last flame dies. Some timed object states are tuned in units that the code reads as two thirds of a Sim minute, so an electric kettle goes cold 200 Sim minutes after it boils.

Objects that several Sims use at once (a bed, a sofa, a dining table) are split into parts, one per seat or spot, and a double bed has 14. Each part lists the parts it overlaps, so a Sim relaxing on the left of a double bed blocks the left-side sitting and pillow-fight spots for everyone else while the right half stays free. Small packs often add objects by copying existing tuning: one stuff-pack candle is an ordinary table candle with one new flame effect.

## Key facts

- An object is an OBJD catalog entry plus one tuning class. `DefinitionManager` reads the OBJD's `TuningId`; 0 or a failed lookup falls back to the prototype tuning 15013.
- Components come from three places: native ids in the OBJD (only Footprint, LiveDrag, Slot and Video have a server side, and only Slot and Video are tunable per object), the 70-entry `_components` tuple of the tuning, and two implicit ones (environment score, utilities). `types.py` defines 110 component slots; 115 decompiled Python classes implement 106 of them (118 classes and 108 names counting the routing and locking classes that only exist as bytecode); 25 classes may be added after creation.
- Live tuning has 2,665 object records. The focus component is on 2,663 and the state component on 2,485 (93 percent); tooltip 2,105, retail 1,857, inventory item 1,331. Lighting is on 91 and flowing puddle on 97.
- Saved components load in priority order: flowing puddle 25, state 20, statistic 10, retail 5, everything else 0.
- `set_state` order: sync-tag copy (init or load only), allowances, add or refuse a missing state, the locked-stat early return, the `ObjectStateChange` event, telemetry, affordance flags, write the linked stat, `_trigger_on_state_changed`, clear caches, push to sync partners.
- A state set while the object is not yet in its manager (all initial states at creation, except `from_creation` sets) runs its client state, its stat listeners and the components' `on_state_changed`, but no state callbacks and no state triggers.
- A stat-backed state follows its stat through listeners on its band edges. When one fires, the new value is the preferred neighbour if its closed range holds the number, else the holding value whose `value` is closest, which makes overlapping bands into hysteresis: the `Dirty` state goes from Clean to Neutral below 50, and back to Clean only above 60.
- `StateTrigger` re-runs its statistic operations, loots and child sets every time it passes; only its random state is skipped when the trigger state is re-entered.
- `TimedStateChange` alarms use `clock.interval_in_real_seconds`, so one tuned unit is 1,000 ticks, 40 Sim seconds. 305 live objects use timed triggers.
- Brokenness (0 to 100, no decay, new objects start at a random 90 to 100) falls only through per-use loots: toilet -6.4, shower -6.7, bath -6, stove and microwave -5, sink -4, fridge -2, each at 67 percent. Broken is 0 to 30.
- The werewolf trait of GP12 (Werewolves) adds a 5 percent chance of -100 to most breakage loots.
- `current_value = max(round((base + statistic bonus) x state_based_value_mod), 0)`. Broken subtracts 0.5 from the modifier and burnt 1.0; the only depreciation is one 20 percent cut after purchase.
- Fire: an object's `commodity_object_burning` starts at 100, drops 2 per new fire and decays at 3 x 1.5 x 2^fires per Sim minute while burning; a fire object's strength decays at 1.111 per minute (90 minutes), times 20 under a sprinkler. Spread is tried every 13 Sim minutes after the first 30.
- Fire insurance adds 50 percent of each covered value loss while a fire burns on the active household's lot, paid when the last fire ends.
- Light dimmer runs 0 to 1, with -1 meaning automatic; the light statistic mirrors it times 100, and power loss forces 0 while remembering the setting.
- Multi-Sim objects are split into parts: 446 live objects carry 2,622 parts (the double bed 14). A part is a proxy of its owner with its own location (a `b__subroot__N` joint), its own slots and its own reservations, and a Sim may reserve it only when every part it overlaps is free for that Sim too.

## How it works

### From catalog entry to live object

- **Observed** (`objects/definition_manager.py: DefinitionManager`, `objects/definition.py: Definition`). A `Definition` is a slotted record built from OBJD properties: `Components` (a uint32 array of native component ids), `Icon`, `Model`, `MaterialVariant`, `ThumbnailGeometryState`, `Rig`, `Footprint`, `TuningId`, `Slot`, `SimoleonPrice` (default 100), environment-score mood tags and scores, and positive and negative environment score. `get_object_can_depreciate` is a native call.
- **Observed** (`DefinitionManager`). The loader takes `TuningId` and fetches that class from the OBJECT instance manager. A `TuningId` of 0 maps to `PROTOTYPE_INSTANCE_ID` 15013 (the record named `prototype`), and a failed lookup falls back to the prototype as well; the log text calls that valid for SP14 (My First Pet) objects that mimic EP04 (Cats & Dogs) ones. Then `get_class_for_obj_state` applies the class's `_object_state_remaps`, `set_class` binds the class, the result is cached under the definition id (or the pair of id and `obj_state` when a state is given) and build/buy tags are assigned.
- **Observed** (`objects/system.py: create_object`, bytecode checked). Creation runs in this order: the native `get_vetted_object_defn_guid` may swap the definition for a fallback; the class is instantiated (which builds the components, below); the caller's `init` callback runs; world-file and conditional-layer objects get persistence group IN_OPEN_STREET; location, id and content source are set; commodity callback alarms may be suppressed; the object is added to the object manager (on lot, world file, open street, household inventory, conditional layer) or the inventory manager (Sim or object inventory); the `post_add` callback runs.
- **Observed** (`indexed_manager.py: IndexedManager.add`). Adding calls every component's `pre_add` before the object is stored in the manager, then sets the id and calls `on_add`. That gap matters for states (see "How a state changes").
- **Observed** (tuning, live). The 2,665 object records split by class into `GameObject` 2,537, `Fish` 26, `Door` 25, `Jig` 20, `PrototypeObject` 17, `Puddle` 9, `SectionalSofaPiece` 8, `Rug` 5, `Sim` 4, `FishBowl` 3 and single records of `Fire`, `FireSprinklerHead`, `Terrain`, `Ocean` and seven more classes. The 28 `Seating` records and the `Television` and `Placeholder` records exist only in the base full build, which the game does not load.

### The component container

- **Observed** (`objects/components/__init__.py`). A component class declares `component_name` (a `component_definition(class_attr, instance_attr)` pair from `types.py`), and optionally `key` (native id), `persistence_key`, `persistence_priority` and `allow_dynamic`. The metaclass fills five registries: `native_component_id_to_class`, `component_name_to_classes`, `component_inames`, `component_definition_set` and `persistence_key_map`.
- **Observed** (`ComponentPriority`). PRIORITY_DEFAULT 0, PRIORITY_RETAIL 5, PRIORITY_STATISTIC 10, PRIORITY_STATE 20, PRIORITY_FLOWING_PUDDLE 25. `components_sorted_gen` visits components by descending priority, then name. `forward_to_components_gen` uses insertion order instead.
- **Observed** (`ComponentContainer.add_component`). Adding raises if the component is already there, then requires `can_add_component`, `is_valid_pack` (the class's `required_packs`, default base game) and `is_valid_to_add`, then sets the attribute named by the INAME and re-sorts. A component whose pack is missing is simply not added. `add_dynamic_component` also requires exactly one class under the name, `allow_dynamic` and `can_be_added_dynamically`.
- **Observed** (`BaseObject.add_component`, `remove_component`). When the object already has an id (it is live), the object-level wrapper calls the new component's `pre_add` and `on_add`; during construction neither runs, and the manager add calls them later. Removal from a live object calls `on_remove_from_client`, `on_remove` and `post_remove`.
- **Observed** (`componentmethod`, `componentmethod_with_fallback`, `ored_forward_to_components`). `@componentmethod` copies a method onto the owner class the first time a component is built, but only where the owner's attribute is still the container's fallback. `componentmethod_with_fallback` installs a default on `ComponentContainer`. The "ored" forwarder returns true if any component does. `ComponentContainer.__getattr__` returns None for any component INAME, so `obj.state_component` is None on an object without one.
- **Observed** (`objects/components/types.py`). 110 `component_definition` lines name 109 distinct slots (ROUTING_COMPONENT appears twice). Eight are client-only native components with fixed keys (Position, Render, Animation, Routing, Sim, Audio, Effects, Gameplay); four native components have server classes (Footprint, LiveDrag, Slot, Video). CHANNEL, OBJECT_LOCKING and PORTAL_LOCKING have definitions but no decompiled class (the locking classes live in `locking_components.pyc`, see "Locking components"). 115 decompiled classes implement 106 names; 45 classes carry a persistence key (38 distinct, eight gardening classes share one). **Observed** (bytecode of the failed modules): three more classes exist only in modules that did not decompile, the server `RoutingComponent` (a second class for ROUTING_COMPONENT, next to the client-only one in `types.py`), `ObjectLockingComponent` and `PortalLockingComponent` (both with their own persistence keys), so 118 classes implement 108 names and only CHANNEL has no class at all.
- **Observed** (`allow_dynamic=True`). The 25 classes that may be added after creation: EnvironmentScore, StageMark, BrandingIcon, Crafting, Heirloom, Jewelry, LineOfSight, LinkedObject, NewObject, ObjectClaim, ObjectFashionMarketplace, ObjectMarketplace, ParentToSimHead, Proximity, SituationScheduler, State, Statistic, Stolen, StoredActorLocation, StoredInfo, StoredObjectInfo, StoredSimInfo, Utilities, WaitingLine, SpawnPoint.
- **Observed** (`BaseObject.__init__`, `ScriptObject.__init__`). A live object gets its components in this order: native ids from the OBJD whose class `has_server_component()`, built from `_components_native` (Slot, Video) or `create_component`; the parts; every enabled `_components` factory, with `get_subcomponents_gen()` children; the persistence group (NONE if `_persistence` is NONE, else OBJECT); a dynamic ENVIRONMENT_SCORE component when the OBJD has a non-zero environment score, mood tags or trait modifiers; a dynamic UTILITIES component when any of the class's super affordances declares a utility (`_setup_used_utilities` collects them into `_used_utilities` at tuning load). `ScriptObject` mixes in `HasStatisticComponent`, which adds the statistic component on the first `get_tracker`.
- **Observed** (`ScriptObject.load`). Saved component records are sorted by priority, highest first. Each is added dynamically if missing; a component that cannot be added goes to `on_failed_to_load_component`.

### The state component: states and values

- **Observed** (`state.py: ObjectState`). A state is a track: `_values` (references), `overridden_by`, `persists_across_gallery`, `sync_tags`, `failed_to_load_state_value`. `values` is sorted by each value's `value` field unless any value is unordered (None).
- **Observed** (`state.py: ObjectStateValue`). A value has `value` (bool, int, float or unordered), `new_client_state` (a `StateChangeOperation`), `tested_client_state_overrides`, `allowances` (in carry, out of carry, inside, outside, on and off natural ground, all default True), `buff_weight_multipliers`, `remove_from_crafting_cache`, `crafting_types`, `force_add_state`, `send_telemetry_on_state_change` and `visual_icon_state`. `calculate_autonomy_weight` multiplies the weights of the buffs the Sim has, starting at 1.
- **Observed** (`CommodityBasedObjectState`, `CommodityBasedObjectStateValue._tuning_loaded_callback`). A stat-backed state adds `linked_stat` and `lot_based` (read the stat on the active lot). Its values add `range` and an optional `default_value`. At load the value's `value` becomes `default_value`, else the range midpoint; `low_value` and `high_value` sit 45 percent of the range width either side of the midpoint. `get_value(stat)` walks `_values` in tuning order and returns the first value with `lower <= v < upper`, taking the upper bound as inclusive at the stat's maximum; no caller of it was found in the decompiled Python. The state code picks a stat-backed value through `get_state_from_stat_value` instead (see "How a state changes").
- **Observed** (live tuning). 4,807 `object_state` records: `ObjectStateValue` 2,675, `CommodityBasedObjectStateValue` 985, `ObjectState` 713, `CommodityBasedObjectState` 283, `VideoChannel` 79, `AudioChannel` 72. The five states on the most objects: `Klepto_Stolen_Object` 1,518, `MaterialisticAdmired` 1,057, `Fire_Object_Burn_Incinerate` 863, `Fire_Object_Burn_material_change` 763, `Quality` 526. Further down (after states such as `MarketableHigherValue` 500 and `DishLocation` 465) come the wear states of this chapter: `BrokenState` 216, `Broken` 211, `Dirty` 178, `DirtyState` 160.
- **Observed** (`TunableStateComponent`). One object lists `states` (each with `default_value` as a reference or a weighted random list, `client_states`, `client_states_overrides`, `reset_to_default`, `reset_on_load_if_time_passes` and five `tested_states_on_*` hooks), `state_triggers`, `unique_state_changes`, `delinquency_state_changes`, `timed_state_triggers` and `overlapping_slot_states`. Live counts: 1,514 objects tune state triggers, 305 timed triggers, 168 delinquency changes; 39 state entries use a random default.
- **Observed** (`StateComponent.pre_add`). For each stat-backed state the linked statistic is fetched or added (`added_by_default`). If the statistic's `initial_tuning._use_stat_value_on_init` is set, the state is set from the stat value with the tuned default as the preferred value. Every other state, plain or stat-backed, is set to its default with `from_init=True` (bytecode checked: the decompiled source nests that call under the linked-stat test, which would skip plain states). Brokenness and dirtiness both use the stat value.

### How a state changes

**Observed** (`state.py: StateComponent.set_state`, bytecode lines 3248 to 3329; `_trigger_on_state_changed`, lines 3354 to 3428).

```mermaid
flowchart TD
  A["set_state(state, value)"] --> B{"sync_tags and (init or load)?"}
  B -->|yes| B1["copy value from a tagged partner"] --> C
  B -->|no| C{"allowances pass?<br/>carry, inside/outside, ground"}
  C -->|no| X["refused, return"]
  C -->|yes| D{"state on object?"}
  D -->|no, force_add_state| D1["add state"] --> E
  D -->|no| X2["return"]
  D -->|yes| E{"from_init?"}
  E -->|no| F{"same value and no force?"}
  F -->|yes| R["return"]
  F -->|no| G["store value"] --> H{"linked stat locked<br/>and not from stat or load?"}
  H -->|yes| R2["return: value stored,<br/>nothing else runs"]
  H -->|no| I["ObjectStateChange event<br/>(only if the value changed)"]
  E -->|yes| J
  I --> J["store, telemetry, affordance flags"]
  J --> K["write value.value to linked stat<br/>(unless the change came from the stat)"]
  K --> L["_trigger_on_state_changed"]
  L --> M["clear caches; push to sync partners"]
```

- **Observed** (`_check_allowances`). The value's allowances are checked against carry, inside or outside, and natural ground (the ground check is skipped on load). A disallowed value is refused: `set_state` returns, and the logger call next to it is silent in a retail game. While the owner has no manager yet (`owner.manager is None`, which includes every initial state set in `pre_add`) the check passes without testing anything. `force_add_state` only lets `set_state` add a state the object lacks; it does not relax allowances.
- **Observed** (`_trigger_on_state_changed`). In order: apply the client state (return if that fails); add the stat listeners; `owner.on_state_changed`, which forwards to the components; part disabling states. Then, if the owner id is not in its manager and the call is not `from_creation`, only `trigger_on_load` timed triggers start and the function returns. Otherwise: the `_on_state_changed` callbacks, stop the old value's timed trigger, start the new value's, and run every `StateTrigger` while the state component still exists and its `_state_trigger_enabled` flag is on (it starts on).
- **Inferred** (from `IndexedManager.add` calling `pre_add` before storing the object). Initial states chosen at creation never run state triggers or callbacks. `object_creation.py` sets its tuned `initial_states` with `from_creation=True`, and festival objects do the same, so those do run them.
- **Observed** (`_add_stat_listener`, `get_state_from_stat_value`, bytecode). A stat-backed value installs two listeners on the linked stat: below its range's lower bound (preferring the next lower value in sorted order) and above its upper bound (preferring the next higher). When one fires, the new value is chosen among the values whose closed range contains the number: the preferred one if it qualifies, else the one with the closest `value`; if none contains it, the closest overall. A stat with `remove_on_convergence` gets seed listeners for its removal.

```mermaid
stateDiagram-v2
  Clean: Dirty_Clean (50 to 100)
  Neutral: Dirty_Neutral (-60 to 60)
  Dirty: Dirty_Dirty (-100 to -50)
  Clean --> Neutral: dirtiness below 50
  Neutral --> Clean: above 60
  Neutral --> Dirty: below -60
  Dirty --> Neutral: above -50
```

- **Inferred** (the listener rule applied to the live `Dirty` ranges). The overlap gives 10-point dead bands: a toilet that just turned Neutral at 49 must be scrubbed past 60 to read Clean again. A read with no preferred value takes the containing value whose `value` is closest: 55 lies in both Clean (`value` 75, the midpoint) and Neutral (0), and 75 is closer, so a fresh read of 55 says Clean.
- **Observed** (`StateTrigger`). Fields: `set_states`, `at_states`, `set_random_state` (weighted, tested), `prohibited_states`, `loot_actions` (LockDoor or UnlockDoor only), `statistic_operations`, `set_on_children`, `trigger_operation` (AND 0, OR 1, NONE 2; default AND) and `trigger_chance` (an optional percent, off unless tuned, which means the trigger always fires; once enabled it defaults to 100). `_check_triggerable` rolls the chance, then the prohibited states, then the operation: AND needs the changed state in `at_states` and all of them active, OR needs it in the list, NONE needs it absent and none active.
- **Observed** (`StateTrigger.trigger_state`, bytecode). The trigger sets `set_states` (skipping values already active), then the random state only when the old value was not the trigger state, then statistic operations, loots and child sets on every pass.
- **Observed** (`TimedStateChange._schedule_trigger_alarm`, bytecode). Each op's time is `trigger_time + uniform(0, trigger_time_random_offset)`, counted from entering the state: the alarm delay is this time minus the previous op's. The alarm is `clock.interval_in_real_seconds(delay)`, 1,000 ticks per unit, while a Sim minute is 1,500 ticks (`REAL_MILLISECONDS_PER_SIM_SECOND` 25 x 60). The tunable is a `TunableSimMinute`, which is a plain `TunableRange` and converts nothing. So one unit is 40 Sim seconds. `TunableStateComponent`'s `verify_tunable_callback` would flag a time that is not later than the previous op's time plus its offset, but that kind of callback never runs in the retail game (`TunableBase.has_verify_tunable_callback` returns False, [0.03](0.03-tuning-system.md#callbacks-and-verify-checks-that-only-run-on-hot-load)), and its `logger.error` is empty anyway, so a badly ordered timed trigger loads without a word.
- **Observed** (`TimedStateChange._timed_trigger_callback`). Failed `trigger_tests` either re-arm the same op (`reschedule_on_failure`) or skip it. Otherwise `states_to_trigger` are set, then one weighted random value among the entries whose tests pass; the loot list runs only if a state was set. The next op is scheduled only while this trigger is still the active one, so any change of that state cancels the rest. `SetStaggeredStateElement` and `set_dynamic_timed_state` add one-op timed triggers at run time. **Inferred** (the save writes only state pairs): no timed trigger is saved, so after a load a `trigger_on_load` trigger restarts from its first op.
- **Observed example** (tuning `object_ElectricKettle`, base delta). `electricKettle_Values_ControlStates_HeatingUp` moves to `WaterReady` after 20 units and `WaterReady` to `Cold` after 300. **Inferred, by arithmetic:** 13.3 Sim minutes to boil and 200 Sim minutes to cool.
- **Observed** (`time_of_day_component.py: TimeOfDayComponent`, 151 objects). A second clock path: per state, a list of hour marks (0 to 24) with a value, loots, a chance and tests. All objects share one alarm per hour mark on the time service; the handler time-slices at 1/30 of a real second per loop and re-arms for the next day. On add or load the component applies the most recent past mark, rolled like any other.
- **Observed** (`delinquency`, `utilities_component.py`). When a utility is cut, `apply_delinquent_states` sets the tuned values for that utility and remembers the previous ones in `states_before_delinquency_dict` (saved); `clear_delinquent_states` puts them back. The utilities component tracks per-utility permission (`allow_utility_usage_dict`), cancels interactions that use a utility the object may no longer use, and offers the off-the-grid toggles 237843 and 237845. Bills themselves are [5.01 Money, bills, perks and rewards](5.01-money-bills-rewards.md).
- **Observed** (`_save_state_data`, `load`, `_load_state_and_value`). Each state saves as a pair of guid64s. `reset_on_load_if_time_passes` saves the default instead of the current value, and `tested_states_on_save` can override it with the first passing test. Load calls `set_state(from_load=True)`. An unknown value uses `failed_to_load_state_value`, else the state keeps its default. A gallery download skips states without `persists_across_gallery`.

### What a state change does to the object

### Fire

**Observed** unless marked (`services/fire_service.py: FireService`, a 0.02 module read for this chapter; `fire/*`, `objects/fire/*`; tuning `services.fire_service`, `commodity_object_burning`, `commodity_object_fire_strength`, `FireState_*`).

```mermaid
flowchart TD
  S["fire starts on the active lot<br/>(SetFireState roll, interaction, or spread)"] --> F["spawn fire object 43993:<br/>strength 100, decays 1.111/min"]
  F --> O["flammable objects under it:<br/>burning -2, decay modifier x2"]
```

- **Allowed at all** (`is_fire_allowed`): the global switch (`fire.toggle_enabled`), the active lot only, and the venue's `allows_fire` ([2.01 Lots, venues and rooms](2.01-lots-venues-rooms.md)). `SetFireState` (the `set_fire` client-state op) starts a fire at the object when `random() < chance` (default 100 percent).
- **Flammable objects.** An object burns when it has `commodity_object_burning` 39470 (`is_object_flammable`). Both burn states link to that commodity (`Fire_Object_Burn_material_change` on 763 objects, `Fire_Object_Burn_Incinerate` on 863, 1,623 objects between them, 3 listing both), and `pre_add` adds a state's linked stat, so these are the flammable objects (**Inferred** chain from Observed parts). Every fire-related object (flammable or `fire_retardant`) is tagged `Fire_Flammable_AutoAdded` and put in the flammable quadtree with its `flammable_area`: a circle of the object radius, plus 0.2 for retardant objects, or the bounding box of the placement footprint's polygon.
- **Burning** (`start_objects_burning`, `set_object_burning`). A new fire burns the flammable objects it overlaps on the same routing surface, skipping ceiling items that are not wall-graph placed. Each one loses `FLAMMABLE_COMMODITY_DECAY_PER_FIRE` 2 and gets a decay modifier of the same 2. Decay modifiers multiply ([3.03 Needs, statistics and commodities](3.03-needs-statistics.md)). The burn commodity decays at 3 per Sim minute toward 0; `Not_Burning` (99 to 100) freezes it (modifier 0) and `Burning` (1 to 99) multiplies by 1.5.
- **Inferred, by arithmetic.** Under one fire an object loses 3 x 1.5 x 2 = 9 per minute and goes from 98 to burnt in about 11 Sim minutes; under two fires 18 per minute, about 5.5 minutes.
- **Outcome.** `FireState_Burn_Material_Change` (0 to 1) sets material state Burnt, cuts the value 100 percent, freezes dirtiness and brokenness decay, and limits the object to a whitelist of interactions led by `fire_ReplaceBurntObject`. `FireState_Burn_Incinerate` (-1 to 1) replaces the object with definition 42736 and cuts the value. When a fire is removed, `_stop_object_burning` drops its modifier and sets any object still above 0 back to 100, so a scorched survivor is fully restored.
- **The fire object** (`Fire_Fire` 38913 on `commodity_object_fire_strength` 39323). `FireState_FireObject_Burning` (1 to 100, default 100) plays `s40_fire` and broadcasters; `FireState_FireObject_Extinguished` (0 to 1) makes it transient, and the service destroys it when unused. Strength decays at 1.111111 per Sim minute. **Inferred, by arithmetic:** an untouched fire lasts about 90 Sim minutes, about 4.5 under a sprinkler (modifier 20). Fires are never saved (`Fire.persistence_group` NONE) and the save is locked while one burns. A fire that burned out by itself stays in the fire quadtree while other fires burn, so spread cannot land on that spot; an extinguished one (`commodity_object_fire_BeenExtinguished` above 0) is taken out. The whole quadtree is dropped when the last fire ends.
- **Spread** (`_spread_fire`, `spread_fire`, bytecode). The spread alarm starts with the first fire, after `FIRE_SPREAD_INTIAL_TIME_IN_SIM_MINUTES` 30, then repeats every 13. Each tick passes when `uniform(0, 1) <= FIRE_SPREAD_CHANCE` (1 live, 0.75 full build). Then up to `MAX_NUM_ATTEMPTS_TO_PLACE_FIRE` 10 attempts: pick a random fire, roll `FIRE_OBJECT_SPREAD_CHANCE` against the floor under that source fire (base 1, x0.5 when the floor tile is not grass, carpet or hardwood, x0 on metal or stone), go `FIRE_PLACEMENT_RANGE` 2 to 3 times `FIRE_QUADTREE_RADIUS` 0.4 (0.8 to 1.2 m) along the fire's facing, turn the source fire to a random facing (so the next attempt aims elsewhere), run the placement tests, spawn on the first success.
- **Placement tests** (`_placement_tests`). A floor that is not a pool, zero water depth, a height step within `FIRE_SPREAD_HEIGHT_THRESHOLD` (code 0.5), plex rules, no overlapping fire, any Sim there passing `FIRE_CAN_SPREAD_TO_SIM_TESTS`, no fire-retardant object.
- **Sims** (`_burn_sim`, `check_for_catching_on_fire`). A Sim at a fire's spot catches fire at `FIRE_SIM_ON_FIRE_CHANCE`: base 100 percent (code default), x0.9 for a Sim in the bathing outfit who also has one of the two clothing-optional lot buffs (one test list, so both must pass), x0.01 with `buff_Fire_WearingFirefighterOutfit`; that pushes `fire_OnFire` 40870 at Critical priority. A routing Sim is checked against fires within `ROUTING_FIRE_CHECK_RADIUS` 0.2 whose strength is above its minimum.
- **Every new fire** (`_spawn_fire`) burns the objects under it, scorches the floor, removes leaf floor features and derails Sims whose path crosses it. **The first fire on the lot** also starts the fire brigade (`situation_Firefighter` at 100 percent with region and object tests, else `situation_IslanderCulture_FireBrigade` at 75 percent with a region test, both delta; the first one that rolls wins), `situation_fire` for the Sims, the fire alarms, the sprinklers, a notification, the save lock, the insurance multiplier and the spread alarm.
- **Alarms and sprinklers.** Alarms (definition 42827) check every `FIRE_ALARM_CYCLE_TIME` 10 Sim minutes for a fire within `FIRE_ALARM_ACTIVATION_RADIUS` 10; once one sounds, the brigade is called if it is not already there and every Sim on the lot outside the brigade is pushed to react. Sprinklers need `Func_Sprinkler` objects (or `Func_Sprinkler_Floor`, delta only); they start after `SPRINKLER_ACTIVATION_TIME` 20 and repeat every `SPRINKLER_RUN_TIME` 5 (20 in the full build). A head spawns at the ceiling over each unsuppressed fire only if level+1 has a floor; heads suppress within 3 m, floor sprinklers within 1.5 m (code defaults). Suppression adds decay modifier 20 to the fire's strength (100 when immediate), marks it extinguished, and sets any Sim's burning stat there to its maximum. `SPRINKLER_PUDDLE_CHANCE` 30 is tuned but no Python reads it.
- **Insurance** (`increment_insurance_claim`, `_award_insurance_money`). Only while a fire is active, on the active household's home or owned zone with a zone director. Each covered value drop adds the loss x `FIRE_INSURANCE_CLAIM_PERCENTAGE` 50 percent (code 60), or instead the object's full catalog value x the multiplier when `FIRE_INSURANCE_CLAIM_MULTIPLIERS` comes out above 1 (delta: 1.3 for a Sim with bucks perk 399821, which no installed tuning defines). The total is paid into the active household's funds when the last fire ends.
- **Scorch cleanup.** Daily at `SCORCH_TERRAIN_CLEANUP_HOUR` 4, burnt floor features on natural ground are removed if no fire is active. `SCORCH_TERRAIN_CLEANUP_RADIUS` is set in neither build (code default 2.5), and no decompiled Python reads it.

### Locking components

**Observed** unless marked (`objects/components/locking_components.pyc`, which did not decompile: every method rescued per function, the three class bodies, `test_lock`'s branches and `_load` read in its bytecode; `routing/portals/portal_component.py`).

- **Two components, one base.** `BaseLockingComponent` tunes `preset_lock_datas` (a list of the variants `lock_siminfo` (default), `lock_clubs`, `lock_situation_job`, `lock_genus`, `lock_ranked_statistic`, `lock_buff`, `unlock_buff`, `lock_creature`, `lock_all_with_sim_id_exception`) and `require_both_side_unlock` (default False; one-way portals only, and the description says it does not work with player locks). `ObjectLockingComponent` is the `_components` entry `object_locking_component`. `PortalLockingComponent` is not a `_components` entry: the portal component's `_portal_locking_component` builds it as a subcomponent.
- **Adding a lock.** Lock data is kept one per lock type. `add_lock_data` takes `clear_existing_locks` (default `CLEAR_ALL`: every player lock is cleared first; the alternatives clear only player locks of other types, or nothing), `replace_same_lock_type` (default True: a lock of the same type is replaced; only with it off is the new data merged into the old) and `refresh` (default True). It then stores the lock, re-evaluates every instanced Sim (and, by default, every routable object) when `refresh` is on, and registers for the lock's refresh events. A buff with `refresh_lock` starting or ending re-evaluates the Sims only. `lock()` adds `DEFAULT_LOCK` (everyone, no exceptions, system priority, both sides) with those defaults, so it also clears every player lock. `unlock()` clears every lock and every Sim's block.
- **What a lock does.** For each Sim, `test_lock` (the resolution above) decides; a locking result records the Sim against this locker, with a flag for both sides. An object lock then hides the object's own super affordances from that Sim (`component_super_affordances_gen` offers them only to Sims the lock does not stop, and to callers with no context). A portal lock instead locks the "there" side of each of the object's portal pairs in that Sim's routing context, the "back" side too for a both-sides result, and with `require_both_side_unlock` also the matching portal on the destination object. Unlocking reverses this once no locker remains; with `require_both_side_unlock`, only after the destination object's lock has released the Sim as well.
- **Saving.** `_save` writes only locks with `should_persist` and player priority. `_load` first removes every player lock (preset ones included), then rebuilds each saved one by type with `ClearLock.CLEAR_NONE`. System presets come back from tuning when the object is built. **Inferred** (from that order): a preset player lock the player removed stays removed after a load, and `DEFAULT_LOCK`, being a system lock, is never saved.
- **Live use** (live tuning). 22 objects use `object_locking_component`, all of them computers, each with one `lock_siminfo` preset; the same 22 carry the SimoCoin farming component. 27 objects enable a portal locking component, with 40 preset entries between them: 24 `unlock_buff`, 4 `lock_buff`, 3 each `lock_ranked_statistic`, `lock_genus` and `lock_situation_job`, 2 `lock_siminfo` and 1 `lock_creature`. None tunes `require_both_side_unlock`.

### Object parts: one object, several Sims

**Observed** unless marked (`objects/part.pyc`, which did not decompile: rescued per function, with the `Part` class body, `get_joint_transform` and `supports_posture_spec` read in bytecode; `script_object.py: ScriptObject.__init__`, `get_part_data`; `objects/parts/part_data.py`, owned by [3.05](3.05-interactions-postures-routing.md); live tuning).

- **What a part is.** When an object is built, one `Part` is made for each entry of its part data. `Part` is a `ProxyObject` over its owner plus `ReservationMixin`: every instance attribute outside its `_unproxied_attributes` (15 of its own: its data, reservation handlers, joint transform, location, slot and posture caches; joined to the four of `ProxyObject`, and every property is added at run time) is read from and written to the owner, so a part shares the owner's states, components and tuning but has its own location, slots and reservations. Setting a part's transform raises an error; parts only move with their owner. Resetting a part resets the owner.
- **Where part data comes from.** An object tunes the deprecated `_part_data` list or `_part_data_map`, keyed by name. Loading the map sorts it by key and turns the adjacent and overlapping key names into indices, so a part's index (`part_group_index`) is its key's place in sorted order, which is why EA's keys start with a number (`00_Relax_Left`, `01_Relax_Right`). With both tunables the list comes first and the map's indices are shifted by its length. Live: 446 objects have parts, 171 through the map and 275 through the old list, none through both; 2,622 parts, from 1 to 25 per object (`object_Fountain_Pet` 25, two hot tubs and a park fountain 20, `object_bedDouble` 14). Eight objects tune a one-entry map; `ScriptObject._get_tuning_suggestions` lists that case, but only for the debug command `tuning.inspect` (untyped, so not registered in a retail game).
- **What a part supports.** Each entry names an `ObjectPart` record (212 live `object_part` records): `supported_posture_types` (empty means all), `supported_affordance_data` (an affordance filter, applied to mixers only with `consider_mixers`), `blacklisted_buffs`, `trait_requirements`, `subroot`, `portal_data` (portals made per part), `can_pick` (default True), `part_surface` (the owner's routing surface, or a fixed surface type) and `on_owning_part_surface`. The most shared are `part_Sit_Bed` (188 parts), `part_SofaNap` (182), `part_Sit_All` (161) and `part_PetSmall_Sofa` (146).
- **Per-part fields in live use**: an explicit subroot index on 2,107 parts (the field is on by default with index 0, which the other 400 keep; 115 switch it off, which makes them base parts at the owner's own transform), overlapping parts on 1,652, a non-empty adjacent list on 1,473, mirroring switched on for 509 (the optional flag is enabled on 891, set False on the other 382), disabling states on 284, transition-cost modifiers on 276, animation overrides on 218, `restrict_autonomy_preference` on 48 and disabling model-suite indices on 8.

**Where a part is.** A part with subroot index n sits on the owner's rig joint `b__subroot__n` (`ArbElement._BASE_SUBROOT_STRING`); a missing joint or rig raises an error (bytecode). `on_owner_location_changed` rebuilds the part's location as that joint times the owner's transform, with a routing surface from `part_surface`, and then updates the parts of objects slotted into it. A `Subroot` record (29 live) lists bone names: `subroot_DiningTable` holds `_ctnm_chr_`, `_ctnm_drink_`, `_ctnm_eat_`, `_ctnm_sitIndividual_`, `_ctnm_sitShared_` and `_ctnm_placemat_`. A part owns those bones with its subroot index appended (`hash32(str(n), initial_hash=bone)`), so **Inferred** (the hash continues over the appended text, as `get_joint_transform_for_joint` appends the index to a string joint name): seat 3 of a dining table owns `_ctnm_eat_3`. The part's `has_slot`, `get_runtime_slots_gen` and `children` see only the owner's slots on those bones, plus the decoration slots the slot component maps to that subroot.

**Sharing an object.**

- **Observed** (`Part.may_reserve`). Before a Sim may reserve a part, every part in its `overlapping_parts` must be reservable by that same Sim. ### Slotting objects into other objects

**Observed** unless marked (`objects/slot_strategy.pyc` and `objects/slot_elements.pyc`, which did not decompile: rescued per function, with `SlotStrategyAutoSlot`, `SlotItemTransfer` and every mangled loop read in bytecode; `interactions/base/basic.py`; `interactions/utils/loot_ops.py: SlotObjects`; live tuning).

- **Slot strategies.** A slot strategy puts objects into a target's runtime slots. Shared tunables (`SlotStrategyBase`): `max_number_of_objects` (default 15, range 1 to 20), `objects_to_slot` (a participant, or `inventory_objects`: the items in a participant's inventory that pass `object_tests`), `slot_clone` (split one item off a stack instead of moving it), `slot_target` (default Object), `require_claiming` (unset leaves the claim alone, False removes the claim requirement, True claims the object) and `use_part_owner` (slot into the owner when the target is a part).
- **`slot_type_strategy`** (the default). One `target_slot_type`. When the candidates come from an inventory, only objects whose valid slot types include it are kept. Each candidate, until the cap, takes the first runtime slot of that type where it is valid for placement. An object in an inventory is removed from it (or cloned); an object outside any inventory is taken only with `allow_transfer_out_of_hh_inventory`, and a household-inventory proxy is first rebuilt from the household inventory data.
- **`auto_slotting`**. A priority list of `slot_types`, kept to those the target provides. Rounds repeat while the last round placed something and the cap is not reached. Per slot type: shuffle the free slots of that type, take the candidates not yet placed, put the first that fits. With `evenly_distribute_slot_types` (default True) the round moves to the next type after one object, so a sales table is stocked small, medium, large, small and so on; without it, each type fills before the next. Every placed object is also registered with the dynamic area service.
- **Who uses them** (live). The element `slot_objects_from_inventory` (`SlotObjectsFromInventory`, 27 interactions; an optional notification when nothing was placed) and the loot `slot_objects` (`SlotObjects`, 4 loots; when nothing was placed it only calls the logger, which is silent in a retail game). Of their 31 strategies, 23 are `slot_type_strategy` and 8 `auto_slotting`. Examples: `gardening_PlantInObject_PutDownSeed_PlantSmall` puts the picked seed into `slot_PlantSmall`; `si_CraftSalesTable_StockTable_NPC` auto-slots from the actor's inventory into `_gameplaySlot_Deco_Small`, `_Medium` and `_Large`; `loot_AnimalObjects_Management_Assign_Chickens` would put up to 8 chickens into `slot_AnimalObjects_ChickenCoop_Inside` (EP11 (Cottage Living) content shipped in the base tuning, inert here).
- **`slot_item_transfer`** (`SlotItemTransfer`, 16 interactions with 22 uses between them: 12 gardening harvest interactions, closing a craft sales table (two), an autonomous easel craft and a vertical garden conversion) goes the other way. For each object from `objects_to_transfer` (its part owner when `use_part_owner_when_is_part`), its children (or the object itself, with `transfer_object_children` off; default on) that pass `object_tests`, run with each as the picked item, go to the Sim's inventory. `always_to_household_inventory` sends them to the household inventory of the active lot's owner instead; `fallback_to_household_inventory` does so only when the Sim's inventory refuses. `transfer_extra_objects` (optional, off unless tuned; once enabled its count, a literal or random value, defaults to 1 in a range of 0 to 10, and its tests run once) adds that many extra items per source object that gave something, as +1 stack counts on random transferred items. `use_gardening_optimization` stacks identical items (same tuning and quality) before the move and destroys the duplicates.

## Data shapes

- **Definition**: native component ids, model, rig, footprint, slot, tuning id, price, environment-score tags and values. One per catalog entry.
- **Object tuning** (`ScriptObject`, `GameObject`): `_super_affordances`, `_components` (70 optional factories), `_components_native` (Slot, Video), `_persistence` (FULL, BUILDBUY, NONE), `_object_state_remaps`, `fire_retardant`, `flammable_area`; `_used_utilities` is derived from the super affordances, not tuned.
- **Component class**: `component_name`, `key`, `persistence_key`, `persistence_priority`, `allow_dynamic`, `required_packs`; hooks `pre_add`, `on_add`, `on_remove`, `save`, `load`, `on_finalize_load`, `component_reset`, `on_state_changed`.
- **ObjectState**: `_values`, `overridden_by`, `sync_tags`, `persists_across_gallery`, `failed_to_load_state_value`; stat-backed adds `linked_stat`, `lot_based`.
- **ObjectStateValue**: `value`, `new_client_state`, `tested_client_state_overrides`, `allowances` (6 flags), `force_add_state`, `buff_weight_multipliers`, `super_affordances`; stat-backed adds `range`, `default_value`; channel values add `show_in_picker` (and `affordance` for video).
- **State component entry**: `default_value` (reference or weighted list), `client_states` (value to operation), `client_states_overrides`, `reset_to_default`, `reset_on_load_if_time_passes`, `tested_states_on_add / post_load / location_changed / reset / save`.
- **StateTrigger**: `at_states`, `trigger_operation`, `trigger_chance`, `prohibited_states`, `set_states`, `set_random_state`, `statistic_operations`, `loot_actions`, `set_on_children`.
- **Timed trigger**: key state value to `{trigger_on_load, ops: [{trigger_time, trigger_time_random_offset, states_to_trigger, random_states_to_trigger, loot_list, trigger_tests {tests, reschedule_on_failure}}]}`.
- **StateChangeOperation**: 55 optional fields, 28 start/stop distributables and 27 attributes (listed above).
- **Saved state component**: `states` and `states_before_delinquency`, each a list of (state guid64, value guid64).
- **Lighting save**: dimmer, previous dimmer, colour, previous colour, pending dimmer, user intensity.
- **Lock data**: `lock_type`, `lock_priority`, `lock_sides`, `should_persist`, plus the type's own fields (household exception, ranks, genders, buffs).
- **Locking component**: `preset_lock_datas` (variant list), `require_both_side_unlock`; runtime `lock_datas` (one per lock type) and `_disallowed_objects` (Sim to locker to both-sides flag). Saved: the persisted player locks, each as type, priority, sides and the type's fields.
- **Part data entry** (`_part_data_map` value, or a `_part_data` item): `part_definition`, `subroot_index` (optional, enabled by default with index 0), `adjacent_parts`, `overlapping_parts`, `parts_to_transition_costs_modifier` (part name to cost), `disabling_states`, `disabling_model_suite_indices`, `is_mirrored`, `forward_direction_for_picking`, `anim_overrides`, `name`, `disable_sim_aop_forwarding`, `disable_child_aop_forwarding`, `restrict_autonomy_preference`, `additional_part_posture_cost`, `current_body_target_cost_bonus`, `posture_transition_target_tag` (`parts_to_transition_costs_modifier` and the last three exist only in the map form).
- **ObjectPart** (`object_part`): `supported_posture_types`, `supported_affordance_data {compatibility, consider_mixers}`, `blacklisted_buffs`, `trait_requirements`, `subroot`, `portal_data`, `can_pick`, `part_surface` (part_owner or override_surface), `on_owning_part_surface`. **Subroot** (`subroot`): `bone_names` (at least one hash).
- **Slot strategy**: `slot_type_strategy {target_slot_type, allow_transfer_out_of_hh_inventory}` or `auto_slotting {slot_types, evenly_distribute_slot_types}`, both with `max_number_of_objects`, `objects_to_slot` (`object_participant {transfer_participant}` or `inventory_objects {inventory_participant, object_tests}`), `slot_clone`, `slot_target`, `require_claiming`, `use_part_owner`.
- **SlotItemTransfer**: `objects_to_transfer`, `object_tests`, `fallback_to_household_inventory`, `transfer_extra_objects {count, tests}`, `use_gardening_optimization`, `transfer_object_children`, `always_to_household_inventory`, `use_part_owner_when_is_part`.
- **Aggregate interaction**: `aggregated_affordances` (list of `{priority, affordance}`), plus for super interactions `sim_to_push_affordance_on` and `use_aggregated_affordance_constraints`.
- **Routing component**: `plan_context_data {default_context, context_age_species_overrides}`, `walkstyle_behavior`, `object_routing_component`.

## For modders

**Tuning to change.**

- *How fast something breaks*: the object's breakage loot (`loot_Statistic_Breakage_*`): `amount` and `chance.base_chance`. The ranges on `Brokenness_*` decide where Broken starts. The upgrade states are the per-object way to halve wear (`stat_use_multiplier`) or stop it (`locked_stats`).
- *What a broken or dirty object does*: the object's own `client_states` entry for `BrokenState_Broken` or `DirtyState_Dirty` (puddles, effects, utility drain). Editing the shared value's `new_client_state` changes every object that does not override it.
- *Value loss*: `change_value` on the state value; `covered_by_insurance` controls whether it feeds a fire claim.
- *Fire*: module tuning `services.fire_service` (spread timing, chance, insurance, sprinklers); per object `fire_retardant` and `flammable_area`; the burn commodity's decay and the burn states' decay modifiers set how fast things burn.
- *Timed states*: `timed_state_triggers` times are in 40-second units, so multiply Sim minutes by 1.5.
- *Front doors*: the venue's `venue_requires_front_door`; module tuning `objects.doors.door_service` for which portal types count.
- *Lights*: `default_dimmer_value`, `light_states` and the `Func_Light_NoAuto_Lights` and `Func_Light_NonElectric` tags.
- *Seats and multi-Sim objects*: the object's `_part_data_map` (one entry per seat or spot) and the `ObjectPart` it names. `overlapping_parts` decides what one Sim blocks; `disabling_states` switch a part off by state; `blacklisted_buffs` and `trait_requirements` keep some Sims off a part (as `part_Sit_Solo_NoToddler` does for toddlers).
- *Stocking and harvesting*: `slot_objects_from_inventory` with an `auto_slotting` strategy fills display slots from an inventory; `slot_item_transfer` empties slots into the Sim's inventory.
- *Who may use an object or door*: `preset_lock_datas` on `object_locking_component`, or on the portal component's `_portal_locking_component`.
- *A new object from an old one*: copy the tuning record of a similar object and change what differs; the stuff packs above do exactly that.

**Commands** (untyped means DebugOnly, which a retail game never registers; see [1.04 Debug tools, cheats and telemetry](1.04-debug-cheats-telemetry.md)):

**Traps.**

- A component that names a missing pack in `required_packs` is silently skipped, even when the object's tuning enables it.
- `force_add_state` does not bypass allowances; a disallowed value still fails.
- A state set on a locked statistic is stored but runs nothing: no event, no client state, no triggers.
- State triggers' stat operations and loots fire on every pass, including re-entering the same value; guard them with `prohibited_states` if they must run once.
- States chosen at creation run no state triggers. Use the creation op's `initial_states` (which passes `from_creation`) or `tested_states_on_add` when a trigger must fire.
- `apply_depreciation` and `SPRINKLER_PUDDLE_CHANCE` look meaningful and are read by nothing in the Python.
- `Dirty_VeryDirty` exists but is not in the `Dirty` state's list.
- A part's index is the sorted position of its key in `_part_data_map`, not its order in the file. Renaming a key can renumber every part after it. Only the old `_part_data` list falls back to index neighbours when adjacency is left disabled; a map entry without an adjacent list has no adjacent parts.
- A part with no `overlapping_parts` blocks nothing else: two Sims can then use parts that occupy the same space.
- `disable_sim_aop_forwarding` on a part looks like a switch but nothing reads it.
- An `AggregateSuperInteraction` whose `sim_to_push_affordance_on` is not the acting Sim fails when it runs (the context is used before it is set). Keep the default.
- Player locks survive a save; system locks, including what `lock()` adds, are rebuilt from tuning and never saved. A preset player lock that the player removed stays removed.
- A stuff-pack object built on a base record is only as different as its tuning diff: SP82's hot tub is SP02's patch-data hot tub with nothing changed.
- Saving with a fire burning is blocked, and fires are never saved.
- The decompiled `state.py` and `fire_service.py` nest several blocks wrongly (`pre_add`, `trigger_state`, `_client_states_gen`, `_trigger_on_state_changed`, `remove_fire_object`, `start_objects_burning`). Every order of operations in this chapter was read from the bytecode; read the bytecode before trusting an indented block in those files.
- `TimedStateChange.trigger_time` says Sim minutes in its description, and the code feeds it to `interval_in_real_seconds`.

## Limits

- Six modules of this chapter have no decompiled source: `objects/part.pyc`, `objects/slot_strategy.pyc`, `objects/slot_elements.pyc`, `objects/base_interactions.pyc`, `objects/components/locking_components.pyc` and `objects/components/routing_component.pyc`. All were rescued per function; what the per-function decompiler still could not rebuild was read in the bytecode: the class bodies of `Part`, `SlotItemTransfer`, `SlotStrategyAutoSlot`, `JoinInteraction`, `BaseLockingComponent` and `RoutingComponent`, and the functions `Part.get_joint_transform`, `SlotItemTransfer._do_behavior`, `SlotStrategyAutoSlot.slot_objects`, `JoinInteraction.get_name` and `BaseLockingComponent._load`. The rescued text of several other functions (`Part.supports_posture_spec`, `SlotStrategyTargetSlotType.slot_objects`, `SelectInventoryObjects.get_objects`, `test_lock`, the aggregate selection loops) nests blocks wrongly, and the order given here was taken from their bytecode.
- `RoutingComponent.maybe_append_reins_animation` (horse reins, EP14) did not decompile even per function and was not read in bytecode; most of `RoutingComponent` (walkstyles, slaves, route events) is described in [3.05](3.05-interactions-postures-routing.md), not here.
- `sims/sim.pyc`, which builds join and ask-to-join interactions, did not decompile; only the names of its `create_join_si` and `create_invite_to_join_si` were read, so when the pie menu offers "join" is not covered here.
- The animal, heirloom, jewelry, marketplace, SimoCoin farming and small business components need packs that are not installed (EP11, EP14, EP17, SP49, SP17, EP18); they were read from code and base-delta module tuning only, and their object tuning was not read.
- The stuff-pack clone comparison covers three packs' patch data; whether other packs build objects the same way was not surveyed.
- `state_change.set_ending_or_on_xevt_target_refs_states` and `transience_change.set_ending` in `state.py` did not decompile; everything else in that module was recovered per function.
- Laundry (SP13) and dust (SP22) are not installed: their object tunings, condition states, rates and visuals cannot be read. Their module tuning ships in the base delta and is quoted as such.
- Buffs 345177 and 345176 (the second instant-break gate), bucks perk 399821 (the insurance multiplier) and `NON_SELLABLE_STATES` value 478568 are not defined in any installed tuning.
- The automatic light schedule, material swaps, floor features (scorch, leaves, dust) and the definition vetting are native.
- The counts are of tuning records; how many of those objects ever appear in a save was not measured.
